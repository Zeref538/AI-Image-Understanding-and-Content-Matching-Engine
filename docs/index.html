Fox, Not Wolf

AI Image Understanding & Content Matching Engine

A blog about red foxes needs a photo of a red fox. Not a wolf that looks a bit like one, and not whatever file happens to be called fox.jpg. This system looks at every image, works out what is in it, matches images to posts by meaning, and says no, with a reason, when nothing fits.

FastAPI and PostgreSQL with local models through Ollama: qwen3.5:4b reads images and posts into validated JSON, all-minilm embeds them, cosine similarity ranks candidates, and a rule-based mismatch guard decides. Batch jobs with leases and retries, a per-call cost log and a budget guard.

    02The problem

    Similarity alone cannot tell a fox from a wolf

    28 of 52 wolf and coyote pairings outscored a real fox

    Turning text and images into numbers and comparing them gets you most of the way. Foxes land near fox posts. But wolves and coyotes land close too, because they share the same shape, fur and snow. On a fox post, ranking by closeness alone is not safe.

    On the 4 fox posts, cosine similarity does not separate the canids. The weakest real fox image scored 0.420; 28 of 52 wolf or coyote pairings scored above it, and the best reached 0.677. A threshold cannot fix that without throwing out real foxes.

    28 of 52

    wolf or coyote pairings on fox posts scored above the weakest real fox (0.420)

    0

    wolves or coyotes suggested for a fox post, once the guard checks what the animal is

    So the ranking stays, and a second step decides: the mismatch guard. It checks the kind of animal, the similarity and the label's own certainty, and every refusal carries the reason.

    03How it works

    Two batch jobs, then a guarded ranking

    A background worker reads the library once. Each photo goes to a vision model that answers in a fixed format: what animal, a caption, some tags. Answers that break the format are retried, then failed with an alert, never stored half-right. Each post gets the same treatment. Then both become vectors, and asking for a post's images ranks them.

    POST /jobs queues tag_images or index_posts. The worker leases items, calls Ollama, validates with Pydantic (invalid output: 3 tries, then the item fails and an alert row is written), stores metadata and tags, and embeds subject, caption and tags. GET /posts/:id/images ranks by cosine similarity, runs the guard on every candidate and saves each as a suggestion to approve or reject. 

    image --vision model--> JSON --validated--> tags + kind_prob --embed--> vector
post  --text model----> JSON --validated--> kind + summary   --embed--> vector

GET /posts/:id/images
  rank by cosine similarity
  guard each candidate:
    flagged?              "Image classification uncertain, held for review"
    kind differs?         "Animal category mismatch: expected fox, detected wolf"
    similarity < 0.45?    "Similarity 0.421 is below the 0.45 threshold"
  first candidate that passes = the suggestion, else "no_confident_match" + reasons

    Python, FastAPI, PostgreSQL 16, Ollama with qwen3.5:4b and all-minilm, Docker Compose. Everything runs locally: $0, no account, no key.

    04The model's own doubt

    Asking the model how sure it is did not work

    Self-reported confidence was 0.85 to 0.98 everywhere; log-probabilities were not

    The brief wanted unsure images flagged, not guessed. My first idea was to ask the model how confident it was. It said 85% to 98% for every single photo, including the ones it got wrong. So I read a different signal: how likely the model thought each word it wrote was. A wolf called "fox" with 42% behind it is a model that is not sure.

    The confidence field the model returns sat between 0.85 and 0.98 on all 50 images, so it cannot rank doubt. Ollama exposes token log-probabilities, so kind_prob is the probability of the animal word itself, with the runners-up stored beside it. An image is flagged when kind_prob < 0.80.

    ImageReallyModel saidpResult
    img-040gray wolffox0.42flagged (wolf was 0.41)
    img-015gray wolfarctic fox0.72flagged
    img-050gray wolfwhite dog0.75flagged

    The model named 3 of the 8 wolves as something else, and all three are flagged, so none can be suggested. The 0.80 line costs two correct images (a wolf at 0.74, a coyote at 0.76) held for review. At 0.60, the wolf called "arctic fox" would have been eligible for fox posts.

    Where each threshold came from

    The similarity line, 0.45, was picked on the tune posts only: it is the strictest value that missed nothing. At 0.50 both dog posts were missed, because their best photos scored 0.49. The 0.80 doubt line was picked by looking at all 50 image labels, so it has no held-out check. That is written down as a limit.

    scripts/eval.py --tune sweeps both thresholds on the 9 tune posts. Every similarity from 0.20 to 0.45 gave 7/7 with no wrong pick; 0.50 dropped the dog posts (best images 0.4896 and 0.4921), 11/13 overall. min_kind_prob was set from all 50 image labels, with no held-out images. Changing either needs no re-tagging: python -m app.reflag re-applies config/guard.json to the stored probabilities.

    06What it cannot tell you

    A small test, one word per animal

    Limits, stated before anyone asks

    • Small eval. 16 posts, 50 images, six animals that are easy to tell apart in text. 13/13 is real but would not survive a harder set unchanged.
    • The doubt threshold has no held-out data. It was picked from all 50 image labels.
    • The guard relies on one word. Posts and images are compared by a one-word kind, with a short synonym list. A post about "wildlife of Yellowstone" has no single kind and would be refused; a topic taxonomy would fix that.
    • Single tenant. One library, one set of posts, no accounts.
    • Embeddings live in a Postgres array and ranking is a loop over 50 vectors. pgvector is the upgrade past a few thousand images.
    07Run it yourself

    Run it yourself

    Needs Docker and Ollama. The 6 acceptance probes start the batch jobs and check every requirement over HTTP.

    ollama pull qwen3.5:4b && ollama pull all-minilm
git clone https://github.com/Zeref538/AI-Image-Understanding-and-Content-Matching-Engine
cd AI-Image-Understanding-and-Content-Matching-Engine
cp .env.example .env
docker compose up -d --build --wait
docker compose exec api python -m app.seed
python scripts/probes.py
docker compose exec api python -m pytest -q
    • EVIDENCE.md: one proof per requirement in the brief
    • probes-run.txt: the acceptance run these cases come from
    • DESIGN.md: schema, job design and the guard's rules
